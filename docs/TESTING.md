## 二、怎么把系统跑起来

```bash
cp .env.example .env      # 至少改掉 POSTGRES_PASSWORD
docker compose up --build
```

等日志出现 `api 已启动`，浏览器打开 <http://localhost:8080>。

> ⚠️ 之后如果需要重启，用 `docker compose down` 或 `docker compose restart`。
> **不要用 `docker compose down -v`** —— `-v` 会删掉具名卷，文件、分类、归档状态全部丢失，
> 重建镜像也无法恢复。

下面所有脚本都在仓库根目录执行，并且要求系统已经起来。

> **这几层共用同一套数据，必须一层跑完再跑下一层，不要并行。**
> 接口验收、浏览器端到端、检索示例都会清空并重建业务数据，
> 同时跑会出现「一边在读、一边被清」的假失败。
> 在界面上归档文件同理 —— 它会改变检索的命中数。

## 三、六层测试怎么跑

### 3.1 静态检查

```bash
gofmt -l .                    # 应当没有输出
go vet ./...
golangci-lint run ./...       # 需要 v2 及以上
```

`golangci-lint` 的检查项写在仓库根目录的 `.golangci.yml` 里，
其中有一条 errcheck 豁免（收尾型的 `Close` 不判错）附了理由，改动前请先读那段注释。

### 3.2 Go 单元测试

```bash
go test ./internal/...

# 竞态检测。本机的 Windows 工具链跑不起来（退出码 0xc0000139，
# race 运行时与 MinGW 不匹配），用 Linux 容器跑：
docker run --rm -v "$PWD:/src" -w /src -e CGO_ENABLED=1 golang:1.27-alpine \
  sh -c 'apk add --no-cache gcc musl-dev && go test -race ./...'
```

覆盖的是几块**纯函数、一处并发、加上日志与配置的装配**，
都属于逻辑密度高、出错时不会报错而只会算错的部分：

| 包 | 测什么 |
| --- | --- |
| `internal/snippet` | 命中片段的取窗：按字符不按字节、大小写折叠、省略号只在真截断时加 |
| `internal/indexer` | 切片不丢字不超上限、行边界优先、重叠尾巴；向量边车客户端的维度与错误处理 |
| `internal/filekind` | 格式清单大小写不敏感，以及「收不收」与「抽不抽正文」两处判断用的是同一份数据 |
| `internal/logging` | 等级解析与非法值拒绝、落盘是真 JSON、角色各写一个文件、清理可重复调用、目录不可写时失败 |
| `internal/config` | 两种 DSN 形式的口令都不出现在 `RedactedDSN` 的输出里；日志与慢阈值变量的默认值和非法值 |
| `internal/httpapi` | requestId 的消毒与回显、访问日志的分级与 `slow` 标记、检索词不进日志、panic 后仍有访问日志 |

`internal/indexer/embed_test.go` 里的 `TestEmbedderIsSafeForConcurrentUse` 需要单独说明：
它**不带 `-race` 运行也会通过**，因为它检测的是数据竞争，而数据竞争通常不表现出症状。
该用例做过反向验证 —— 把 `Embedder.dimension` 改回普通 `int`，`go test -race` 会在此处报
DATA RACE。因此修改该部分代码时请连带 `-race` 一起运行。

### 3.3 接口层验收（`scripts/acceptance_api.py`）

```bash
docker compose up -d
python scripts/acceptance_api.py            # 会先清空业务数据再开始
python scripts/acceptance_api.py --keep     # 保留现有数据，只跑断言
```

28 节、274 条断言，逐条对着验收条件写。其中第 28 节是回收站
（移入 / 恢复 / 彻底删除 / 清空）—— 验收条件里没有这一条，是交付前补的体验改进，
它的重点在于「删掉的东西在列表、关键词检索、语义检索三处都不可见」，
三处共用同一个过滤条件，所以这一节既验了删得掉，也验了搜不出来。
使用 Python 标准库手工拼接 multipart 而不用 `curl`
是有原因的，理由写在脚本文件头：Windows 上的 `curl.exe` 会按本地代码页转码命令行参数，
用它测中文文件名和中文标签会得出「服务端乱码」的错误结论。

这一层跑完会在库中留下较多副本（归档、改名、重试各留一份），
**要接着跑 §3.5 的示例请先 `--reset`**，理由见 [`RETRIEVAL-EXAMPLES.md`](RETRIEVAL-EXAMPLES.md)。

### 3.4 浏览器端到端（Playwright）

```bash
cd web
npx playwright test            # 37 条
npx playwright test --ui       # 想看过程时用
```

用的是系统已装的 Edge（`channel: 'msedge'`），不需要额外下载浏览器。
`workers: 1`、`fullyParallel: false`：用例之间有共享的服务端状态，并行跑会互相干扰。

五个 spec 分别对应文件、分类、检索、拖拽、布局五条主线。拖拽用例只能逐步骤驱动
`page.mouse`（`down` → 等过长按闸门 → `move` → `up`），不能使用 Playwright 的 `dragAndDrop`：
那是 HTML5 原生拖拽，与这里用的 pointer 事件 + 380ms 长按闸门是两套无关的机制。
注意 `npm run build` **不做类型检查**，类型检查是单独一条 `npm run type-check`。

### 3.5 5 组自然语言检索示例（`scripts/semantic_examples.py`）

```bash
python scripts/semantic_examples.py --reset
python scripts/semantic_examples.py --reset --json docs/semantic-examples.json
```

`--reset` 会清空业务数据、重新灌入 10 份语料、等索引完成，再跑 5 组提问。
必须重置才能复现交付文档中的那张表，原因见 [`RETRIEVAL-EXAMPLES.md`](RETRIEVAL-EXAMPLES.md) 最后一节。

### 3.6 从零启动的冒烟测试

前面几层都在一套已存在的具名卷上运行，也就是说**迁移文件从未在一个空库上从头执行过**。
验收条件第一条却是「按 README 完成必要配置后 `docker compose up --build` 启动系统」，
所以这一步必须单独验。

用另一个 compose 项目名启动一套干净的栈，端口也换掉 —— 这样不会影响现有数据，
也不必冒着删卷的风险验证：

```bash
# LOG_HOST_DIR 必须换一个：日志文件名按角色固定，两套栈写同一个 api.log 会让轮转互相踩
LOG_HOST_DIR=./logs-clean WEB_PORT=8091 docker compose -p kaoheclean up -d --build

# 对着 8091 跑一次冒烟：健康接口 → 校验迁移与迁移文件一一对应 → 确认起点是空库 →
# 上传 10 份语料 → 等索引 → 关键词检索 → 语义检索 → 下载逐字节比对 → 建分类 / 移动 / 归档
python scripts/clean_start_smoke.py

# 验完拆掉，注意只删这个项目的卷
LOG_HOST_DIR=./logs-clean docker compose -p kaoheclean down
docker volume rm kaoheclean_pgdata kaoheclean_uploads && rm -rf logs-clean
```

`--project`（compose 项目名）与 `--base`（接口地址）是配对的，默认值就是上面这一对。
两处必须指向同一套栈：脚本要清空数据、要读 `schema_migrations`，这两件事都不在接口里，
只能进容器做。配错会变成「读 A 栈、清 B 栈」。

两个容易出错的地方，脚本里都写了注释：索引成功的终态是 `ready` 而不是 `indexed`；
PDF 的状态是 `not_supported`（仅存储）而不是 `failed`。

**本次记录**：`migrate` 在空库上依次应用了 `0001_init.sql` 与 `0002_category_no_self_parent.sql`
（`applied=2`），五个服务全部 healthy；冒烟 **PASS=25 FAIL=0** ——
迁移记录与迁移文件一致，10 份文件全部落位，7 份 `ready`、3 份 `not_supported`，
两种检索都有结果且语义检索首位命中 `01_代码提交规范_v2.1.md`，
下载 sha256 与原文件一致，建分类 / 移动 / 归档后默认列表与归档区计数都对。

### 3.7 持久化演练（`scripts/persistence_check.py`）

这条验收条件没法一个脚本跑完，因为中间那一步停机必须在脚本之外发生 ——
脚本依赖的服务正好就是被停掉的那个。所以拆成两段：

```bash
# 先在界面上传几份文件、建几个分类、归档一份，然后：
python scripts/persistence_check.py snapshot

docker compose down            # 注意：不要加 -v
docker compose up -d

python scripts/persistence_check.py verify
```

`verify` 逐项比对停机前后的：文件清单（含每份文件的 sha256 与原文件逐字节比对）、
分类树、归档集合、关键词检索结果（含顺序）、语义检索首位与相似度，
并检查挂载的具名卷确实是同一份。挂到新卷上等于数据从零开始，
「未报错但数据消失」是最难排查的一类。

### 3.8 日志系统

日志不是验收条件里的条目，是本次另外加的一项能力，所以它的验证单独记在这里 ——
几项行为只能通过修改配置、产生真实流量观察，仅审查代码不足以确认。

**分级**（`LOG_LEVEL=error`）：三个返回 200 的请求留下 **0 行**访问日志；
停掉 `db` 制造的真实 500 仍然被记录，且为两条 —— 一条 `failInternal` 带错误原因，
一条访问日志带 status 与耗时，两条的 `requestId` 相同：

```jsonc
{"level":"error","msg":"请求处理失败","requestId":"cf2d41250d045bec","path":"/api/v1/documents",
 "error":"查询文档列表失败: failed to connect to …"}
{"level":"error","msg":"请求","requestId":"cf2d41250d045bec","status":500,"costMs":7993.27,"slow":true}
```

500 记两条是**有意为之**：一条说明原因，一条记录结果。把 `requestId` 对上即可还原整次请求。

**慢标记**（`SLOW_REQUEST_MS=1` / `SLOW_TASK_MS=1`）：同一批请求里
耗时 1.19ms 的那条升到 `warn` 并带 `slow=true`，0.29ms 的仍是 `info`；
worker 侧 `索引完成` 升到 `warn` 并带 `slow=true`，**消息文本一个字未改**，
`grep 索引完成` 仍然可以匹配到全部。

**脱敏**。口令（21 字符）在三个日志文件里 0 命中。更有意义的是第二条：
上传一份正文里嵌了唯一哨兵串 `ZQXSENTINEL7F3A9B2C` 的 Markdown，
等它索引完成后 —— 库里 `document_chunks` 有 **12 个片段**含这个串（对照组成立），
而三个日志文件与全部 stdout 里 **0 命中**。这条才是能捕获 `ParameterizedQueries`
回归的检查：GORM 默认打印参数已插值的 SQL，正文会整批进日志。

**轮转**（`LOG_MAX_SIZE_MB=1`）：打满 1 MiB 后切出一份 1,048,342 字节的历史文件、
并新建 `api.log` 继续写。切出来的名字是 `api-2026-10-06T07-11-28.268.log`
（lumberjack 的带时间戳约定，不是 `api.log.1`）。

**退出**：`docker compose stop api` 后 stderr **没有** `invalid argument`。
这一条单独看不足以说明问题 —— 因此同时确认了进程确实执行到收尾路径：
`收到退出信号，正在关闭 api` 这行确实写入了文件，说明 `Sync` 与关闭流程已执行且未报错。

**panic 路径**未实际构造（`documents.go` 中那个 panic 需要 `crypto/rand` 失败才触发），
改用中间件单测断言：返回体是 `{"code":"internal_error",…}` 的 JSON、
恰好一条带 `stack` 的 Error 日志、且**恰好一条** status=500 的访问日志。
该用例做过反向验证：把中间件顺序换回 `gin.Recovery(), AccessLog()`，它会失败。

**容器重建后日志延续**：`docker compose down` + `up -d` 之后三个文件都还在并继续追加
（561→595 / 4→6 / 31→34 行），没有截断也没有 NUL 字节。

> 一处已记录的坑：容器仍在运行时从宿主机 `> logs/api.log` 截断文件，
> 会使它继续按旧偏移追加，中间留下一段 26 万字节的 NUL 填充。
> 清日志需先停止容器，或者交由轮转处理。

## 四、验收条件逐条对照

### 4.1 Docker 部署

> 提供 Dockerfile 和 Docker Compose 配置，按 README 完成必要配置后，可通过 `docker compose up --build` 启动系统

`Dockerfile` 一条多阶段构建，产出 `api` / `worker` / `migrate` 三个角色共用的镜像
（同一个二进制，靠 `--mode` 区分），避免三份依赖版本各自漂移。
`web` 用的是独立的 `web/Dockerfile`（Node 构建 → nginx 托管）。

`.env.example` 里列了全部必填项，`docker-compose.yml` 用 `${POSTGRES_PASSWORD:?未设置：请先执行 cp .env.example .env}`
这种写法，缺了它会直接报出该怎么办，而不是起来一个连不上数据库的容器。

只有 `web` 映射宿主机端口，`db` / `api` / `worker` / `embed` 都只在 compose 内网互通，
不会跟本机已有服务抢端口。

**本次记录**：`docker compose build api` → `docker compose up -d`，五个服务全部起来，
`api` 与 `db` 健康检查为 `healthy`。

这一条的重点是**空库**：在既有卷上能启动，不代表迁移语句在一个从未执行过的库上也正确。
因此另外用 `-p kaoheclean` 启动了一套干净的栈（端口 8091，不影响现有数据），
在空库上从头执行迁移后再冒烟一遍 —— 见 §3.6。

### 4.2 上传下载

> PDF、TXT、Markdown 均可上传和下载，下载内容与原文件一致

「下载内容与原文件一致」是按字节逐一比对的，不是比较大小 ——
接口 §7 与持久化演练里都对下载回来的字节算了 sha256。
PDF 的下载另外验了 Range 请求（§8），因为在线预览依赖它。

**本次记录**：接口 §1/§2/§7/§8 全部 PASS；浏览器 01-documents 15 条 PASS。

### 4.3 分类调整

> 新建分类、移动文件后，列表和筛选结果正确，刷新后仍保留

接口 §13–§16 覆盖建树、归属、移动、删除；其中删除分类用 `ON DELETE SET NULL`，
文件转为「未分类」而不是被一起删掉。

「刷新后仍保留」这一半是浏览器用例 `02-categories.spec.ts` 里那条
「刷新后分类结构与文件归属都还在」验证的，它确实调用了 `page.reload()` ——
前端若把状态放在内存里，这条用例会失败。

**本次记录**：接口 §13–§16 全部 PASS；浏览器 02-categories 11 条 PASS。

### 4.4 关键词搜索

> 能通过文件名及 TXT／Markdown 正文关键词找到目标文件，分类筛选同时生效

实现是 pg_trgm 的 GIN 三元组索引 + `ILIKE`，中文不需要分词。
这一节的断言是**行为式**的，不写死命中份数：语料里提到过某个词的文档会随语料变化，
而这一节要验的是「文件名命中排在前面」「正文命中带得出片段」这两条排序规则。

空结果、空关键词（400）、超长关键词（400）、非法分类筛选（400）也一并验了。

**本次记录**：接口 §24 全部 PASS；浏览器 03-search 5 条 PASS。

### 4.5 语义检索

> 使用与原文措辞不同、含义相关的问题，能返回相关文档及片段；代码中存在真实的向量生成、存储和检索流程

「真实的向量生成、存储和检索」是本节的核心，链路如下：

| 环节 | 在哪 | 做什么 |
| --- | --- | --- |
| 生成 | `services/embed/app.py` | ONNX Runtime 跑 bge-small-zh-v1.5（int8），CLS 池化 + L2 归一化，输出 512 维 |
| 生成 | `internal/indexer/embed.go` | Go 侧的边车客户端，分批调用、校验维度与条数 |
| 存储 | `internal/store/jobs.go` + `internal/migrate/sql/` | worker 领任务，写入 `document_chunks.embedding vector(512)`，建 HNSW `vector_cosine_ops` 索引 |
| 检索 | `internal/store/search.go` | 用 `<=>` 算余弦距离，按片段打分、按文档聚合 |

没有调用任何托管检索服务；模型是本地加载的（`services/embed/model/model.onnx`，24 MB）。

再说「措辞不同」。5 组示例都刻意满足同一个条件：**把整句话原样丢进关键词检索，命中数为 0**。
完整对照表与原文片段见 [`RETRIEVAL-EXAMPLES.md`](RETRIEVAL-EXAMPLES.md)。

相似度下限 `SEMANTIC_MIN_SCORE` 默认 `0.5`，是按当前模型在验收语料上标定出来的：
相关结果的首位相似度在 0.618~0.717，语料里没有对应内容时的最高分在 0.44~0.47，
0.5 落在这段空档里。标定过程与换模型后必须重新标定的原因见 [`DESIGN.md`](DESIGN.md) §4.3。

### 4.8 异常处理

> 对超限文件、上传失败、索引失败和无搜索结果提供明确反馈，允许合理重试

| 情形 | 反馈 | 验在哪 |
| --- | --- | --- |
| 超限文件 | 413 + 说清上限是多少 | 接口 §12；浏览器 01-documents 的「超过上传上限」1 条 |
| 不支持的格式 | 400 + 列出支持哪些 | 接口 §3；浏览器 01-documents 的「拒绝不支持的格式」1 条 |
| 上传失败 | 错误原因可见，可重试 | 接口 §12；浏览器 01-documents 的「服务端拒绝后重试」1 条 |
| 索引失败 | `failed` 状态 + 错误原因 + 「重新索引」入口 | 接口 §20/§21/§22；浏览器 01-documents |
| 无搜索结果 | 与「还没搜过」区分开的空态 | 接口 §24；浏览器 01-documents、03-search |
| 向量边车不可用 | 语义检索 503，其余功能不受影响 | 接口 §26 |

两处需说明分工，否则上表容易被误读为「浏览器验证了服务端的拒绝」：

- **超限**：浏览器里走的是**前端预检**。上限由 `/config` 下发、前后端共用一份，
  所以界面上根本到不了服务端那一步，服务端的 413 在浏览器里按设计不可达，
  只有接口 §12 直接打接口覆盖得到（那里刻意绕过前端）。
  浏览器用例覆盖的是另一半：用户看到的提示是否正确、上限来自服务端还是前端硬编码。
- **上传失败**：形态与格式两边共用 `/config`，前端先拦下了，所以浏览器里能走到的
  服务端拒绝只剩标签数量一项（前端不预检它）。用例正是用 21 个标签越过
  `maxTagCount=20` 实现的，见 01-documents 最后一条。

索引失败不影响原文件的保存与下载：§21 专门断言失败之后原文件仍能下载且逐字节一致。
重试是有限次的（`max_attempts`），退避 15s/30s，超过上限才转 `failed` ——
无限重试会把一个必然失败的任务变成永久占用。

### 4.9 操作体验

> 上传、整理、查找和下载流程连贯，主要入口清晰，常见屏幕尺寸下无明显布局问题

**已验到的**：上传有进度条；列表页有加载态、空态、错误态三种区分；
只要还有文件停在待索引/索引中，列表每 1.5 秒静默刷新，全部落定后自动停下；
索引状态用不同标签与颜色区分「已索引 / 索引失败 / 仅存储」，
`not_supported` 是正常状态而非失败，详情页也不会给它「重新索引」按钮 ——
提供一个按了也不会成功的按钮比不提供更糟。

**删除与归档的反馈强度按「能不能反悔」分级**：移入回收站不弹确认框，
改为在提示上挂一个 6 秒的「撤销」（比默认的 3 秒长 —— 撤销是要用户做个决定的，
一闪而过等于没给这个机会）；真正毁数据的动作（彻底删除、清空回收站）才弹红色确认框，
文案写明「无法恢复」。彻底删除只对回收站里的文件生效，想毁掉一份正在用的文件必须走两步，
多出来的这一步就是误删可以停下来的地方。
分类的删除入口原本藏在悬停才出现的「···」菜单里，用户无法发现，现在改成每行常显的三个图标按钮 ——
无法被发现的删除入口与不提供删除入口等价。

同一套判断也决定了拖拽的形态：**纯长按没有任何可见线索**，因此行首常显一个抓手图标，
长按行内任意位置与按住抓手都能拖。拖动过程中有跟随指针的文件条、行间插入线、
悬停分类节点时该行高亮，松手前用户即可知道会落到哪里。
反过来，**拖动排序不提供撤销，拖入分类提供** —— 排序结果直接可见，拖回原位是同样的手势；
「移入分类」之后该文件已从当前视图消失，因此按上面的规则挂 6 秒撤销。
反馈强度依据「用户能否自行回到原状态」，而非「哪个操作更轻」。

**常见屏幕尺寸下没有布局问题**：这条原先只能靠肉眼，现在由 05-layout 的 2 条用例守着 ——
在 1280 / 1366 / 1440 / 1920 四档下直接量表格滚动容器的 `clientWidth` 与 `scrollWidth`，
并要求三个 tab 的操作列按钮都落在可视区内。之所以要直接测量而非以「点得到按钮」代替，
是因为 Playwright 点击前会先将元素滚入视口，横向溢出正是它无法发现的一类问题：
加这条用例之前，1280 下各列宽度合计 1104 而容器只有 934，右对齐的操作列整排落在屏幕外，
只能横向滚动表格才能点击，而当时的浏览器用例全部通过。

**没有验到的**：窄屏那一档。05-layout 覆盖的四档都还在左右分栏的布局里，
再窄下去会走 `@media (max-width: 900px)` 的上下排列分支，那条只有手工拖过窗口。见 §6。

## 六、没有验证到的部分

按「如果有人照着这份文档验收，会踩到什么」的顺序列：

1. **窄屏（≤900px）下改为上下排列的那一档没有自动化用例**。
   05-layout 覆盖的是 1280 / 1366 / 1440 / 1920 四档（1280 是当初真正出问题的那档），
   都还在左右分栏的布局里；再窄下去会走 `@media (max-width: 900px)` 那条分支，
   而那条分支只有手工拖过窗口。如果验收方在平板竖屏上打开发现布局问题，
   属于没有验到的地方。
2. **并发上传没有压力测试**。接口验收是串行的。多用户同时上传时，
   `FOR UPDATE SKIP LOCKED` 的任务领取与部分唯一索引在数据库层是有保证的，
   但没有用并发用例实测过。
3. **`-race` 只在 Linux 容器里跑过**，本机 Windows 工具链跑不起来（0xc0000139）。
   交付的镜像是 Linux，所以这不算盲区；但如果有人在 Windows 上直接 `go test -race`，会失败。
4. **语义检索的相关性只用 5 组示例衡量过**。没有标注数据集，没有 recall/precision 指标，
   阈值是按这 5 组正例加一批无对应内容的提问标定出来的。
5. **PDF 正文检索不到**，这是**尚未完成的功能**，不是设计取舍（[`DESIGN.md`](DESIGN.md) §3.5）。
   这里要更正一个曾经写错的结论：本文档先前记录「验收语料那 3 份 PDF 内嵌字体缺少
   Unicode 映射，即使接上解析库也搜不到」——**这是错的**。用 `pypdf` 实测，
   3 份 PDF 分别能取出 1005 / 996 / 941 个汉字。当初的结论来自一次有缺陷的手工解析
   （只解了一层 `FlateDecode`，而实际过滤器链是 `[/ASCII85Decode /FlateDecode]`；
   字体资源名正则写成 `/F\d+`，实际形如 `/F2+0`），**是解析代码的问题被当成了语料的问题**。
   因此 PDF 索引是待补的功能缺口，验收时若被问到，以此为准。
6. **没有身份认证与权限**。任何能访问端口的人都能读写全部文件，见 [`DESIGN.md`](DESIGN.md) §5 第 1 条。
7. **`scripts/persistence_check.py` 需要人工在两个脚本之间执行停机**。
   停机这一步骤应由人工确认，因此没有做成一个脚本自动跑完。
8. **浏览器用例用的是系统 Edge（`channel: 'msedge'`）**，只在 Edge 上跑过，没有跨浏览器矩阵。
9. **「彻底删除一个正在索引的文件」只手工验过一次，没有进自动化套件**。
   它没法写进默认套件：这个时序要求恰好在上传完成、worker 正在抽取正文时按下彻底删除，
   换一台机器（或换一次编译）就会变成随机红灯。
   本次用一个 440 KB 的 Markdown 手工验证过 —— 轮询到 `processing` 后立即软删除再彻底删除，
   worker 那一轮留下的 `索引完成` 那条日志带着 `documentId=21`、`attempt=1`，耗时 15.41s：
   整条抽取与向量链路跑完、真正要写库时才发现文档已经不在了，于是提交一个空事务干净退出。
   事后查库：该文档的 `documents` 行、`document_chunks`、`index_jobs` 残留都是 0，
   全库也没有孤儿片段、孤儿任务或失败任务。

   > 上面那次运行发生在引入 zap 之前，所以当时的日志是 `documentId=21 attempt=1 cost=15.41s`
   > 这样一行纯文本。现在同一条日志是 JSON，会多出 `jobId`、`chunks`、`truncated` 三个字段，
   > 耗时也从 `cost=15.41s` 变成 `costMs=15410.12` 这样的浮点毫秒 ——
   > 单位写进键名，是因为纯数字无法表达量级；使用浮点是因为本系统的请求经常在 1 毫秒以下，
   > 整数毫秒会把它们全部压成 0。**消息措辞一个字未改**，`grep 索引完成` 仍然可以匹配到全部。

   保证它成立的是 `internal/store/jobs.go` 里 `CompleteIndexJob` 的守卫 ——
   **先更新 `documents`，受影响行数为 0 就直接返回**。没有这个顺序，
   这次写入会撞上外键、被记成一次失败并重试三次，而重试永远不可能成功。
   这条守卫因此不只是优化，删掉它这个场景就会退化成噪声。

   代价需要说明：**这条守卫没有自动化用例**。`internal/store` 目前一个测试文件都没有
   （有单测的只有 `filekind` / `indexer` / `snippet` / `logging` / `config` / `httpapi`），
   要测它得先给 store 层引入测试数据库基建（sqlite 驱动或 testcontainer），
   那是独立的一次决定，不在本次范围内。这里给出的证据是代码本身加事后查库的结果。

10. **拖动排序的核心逻辑同样没有自动化单测**。`store.MoveDocumentAfter`
    （锁表读全序、摘出被拖行、定位锚点、拼接新序、一条语句写回）与上一条是同一个盲区：
    `internal/store` 没有测试基建。这次给出的证据是浏览器用例
    （重排后 `page.reload()` 顺序不变、拖入分类、撤销、回收站不给拖）
    加一轮手工接口验证：未知锚点 400、未知文件 404、`afterId` 指向自己时无操作、
    空 body 置顶，以及一次真实的移动在列表里复核无误、事后查库与移动前的顺序逐项一致。
    没进自动化套件的边界有两条：**并发拖动**（两行几乎同时被拖走，
    代码里靠 `FOR UPDATE` 串行化，但没用并发用例实测过）与**跨页拖拽**
    （按设计就不支持，见 [`DESIGN.md`](DESIGN.md) §5 第 15 条）。

11. **多文件上传没有自动化用例**。上传对话框能一次选中多个文件、按顺序逐个提交，
    这条路径只有人工验证过：现有 e2e 里的 `setInputFiles` 全是单个文件，
    没有一条走「一次选多个」的入口。
    它比表面上更容易出错 —— 批量队列、每个文件各自的进度与状态、部分失败时的收尾，
    都是单文件路径不会经过的分支；上表 §一第 2 行那句「浏览器 01-documents 15 条」
    覆盖的是上传与下载本身，不含多选。
    下一次动上传的时候，这里是最先该补的一条用例。
