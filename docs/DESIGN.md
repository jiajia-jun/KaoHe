## 1. 架构总览

```
                 ┌──────────────────────────── 宿主机只暴露 ${WEB_PORT} ───┐
                 │                                                          │
   浏览器 ───────┼──▶ web (nginx)  ──/api/──▶  api (Go + Gin)  ──▶ db (PostgreSQL 16)
                 │      静态资源                 ▲                    pgvector
                 │                               │                    pg_trgm
                 │                               │                        ▲
                 │                          worker (Go)  ──/embed──▶ embed   │
                 │                        索引任务消费者          (ONNX)     │
                 │                                    │                    │
                 │                                    └── 读原文件 ─────────┘
                 │                          uploads 具名卷      pgdata 具名卷
                 └──────────────────────────────────────────────────────────┘
```

六个容器，各自只做一件事：

| 服务 | 角色 | 说明 |
| --- | --- | --- |
| `web` | 前端 + 反向代理 | nginx 托管 Vite 构建产物，把 `/api/` 反代到 `api` |
| `api` | 对外 HTTP 接口 | 文件、分类、检索；不持有任何推理依赖 |
| `worker` | 索引任务消费者 | 抽取正文 → 切片 → 请求向量 → 写库 |
| `embed` | 向量边车 | ONNX Runtime 跑 BGE 中文模型，只提供 `POST /embed` |
| `db` | 数据库 | 关系数据 + 向量 + 任务队列，一个引擎承担三件事 |
| `migrate` | 一次性迁移 | 建扩展、表、索引；成功之后 `api` 才启动 |

`api`、`worker`、`migrate` 是**同一个镜像**的三个 `--mode`，避免三份依赖版本各自漂移。
数据落在 `pgdata` 与 `uploads` 两个具名卷上，容器重建不影响数据。

### 1.1 上传与索引的数据流

上传走的是「先落库、再异步建索引」，两条路径互不阻塞：

```
POST /documents
  ├─ 原文件写入 uploads（临时文件 + rename，原子替换）
  ├─ 同一个事务里写入 documents 行与 index_jobs 行
  └─ 立刻返回 201，indexStatus = pending

worker 轮询 index_jobs（FOR UPDATE SKIP LOCKED 领任务）
  ├─ 按扩展名判断是否可抽取正文（PDF 直接标 not_supported 并结束）
  ├─ 抽取 → 切片（行边界优先，相邻片段重叠 80 字符）
  ├─ 分批请求 embed，拿到 512 维 L2 归一化向量
  └─ 在同一事务里覆盖写入 document_chunks，并置 documents.index_status

失败路径：写入 index_error、按 15s/30s 退避重试，超过上限置 failed；
         用户可在详情页点「重新索引」。整个过程不动原文件。
```

把任务行和文档行放进同一个事务，是为了消灭「文件已存但索引任务丢了」的窗口 ——
这是引入独立消息队列后最容易出现、也最难排查的一类不一致。

### 1.2 检索的两条路径

| | 关键词检索 | 语义检索 |
| --- | --- | --- |
| 入口 | `GET /api/v1/search?q=` | `POST /api/v1/search/semantic` |
| 匹配依据 | 文件名 + 正文片段的字面子串 | 查询向量与片段向量的余弦相似度 |
| 排序 | 文件名命中优先，其次按上传时间 | 相似度降序 |
| 结果 | 命中片段（关键词前后各 48 字的窗口） | 命中片段（原文整段，不二次截取） |
| 降级 | 无外部依赖 | 边车不可用时返回 `503 service_unavailable` |

两条路径共用同一份 `document_chunks`：切片只做一次，关键词命中与语义命中看到的是同一段文字，
结果列表的渲染也复用同一个组件。分成两套切片会让「同一份文件在两种检索里读出不同段落」。

**向量检索一定是「最近邻」，不是「相关」**：即使语料里根本没有对应内容，它也会返回最像的几条。
因此相似度下限（`SEMANTIC_MIN_SCORE`）不是调优参数，而是把「没有相关内容」变成空结果的开关。
标定过程见 §4.5。

## 3. 关键取舍

### 3.1 用 PostgreSQL 表当队列，而不是引入 Redis

`index_jobs` 就是队列，`worker` 用 `FOR UPDATE SKIP LOCKED` 领取任务。

- **换来什么**：文件落盘、`documents` 行、`index_jobs` 行可以在同一个事务里写完，
  不存在「文件已保存但任务丢失」的中间态；少一个容器、少一份要备份的数据。
- **代价**：任务吞吐量受数据库限制。本平台是单机内网部署，索引任务以个位数/分钟计，
  这个上限离我们很远。
- 「同一文档同时只允许一个未完成任务」用**部分唯一索引**在数据库层强制
  （`index_jobs_active_key ... WHERE status IN ('queued','running')`），
  而不是靠应用层先查后写 —— 后者在并发下必然漏。

### 3.2 中文全文检索用 pg_trgm，不用 tsvector

PostgreSQL 的全文检索依赖分词器，而 `tsvector` 对中文默认按空白切词，一整句会变成一个词元。
pg_trgm 按字符三元组建索引，中文不需要分词也能让 `ILIKE '%词%'` 走索引。

- **换来什么**：改一处配置就能用，不需要在数据库里装 zhparser / pg_jieba 这类分词扩展。
- **代价**：关键词检索是**字面匹配**，没有词干还原与同义词。
  这正是语义检索存在的理由 —— 交付文档里那 5 组示例都是「整句在关键词检索里 0 命中、
  语义检索首位命中预期文件」的形态。

### 3.3 检索与任务领取用原生 SQL，CRUD 用 GORM

向量距离运算、递归 CTE 分类树、`FOR UPDATE SKIP LOCKED`、窗口函数取每篇的前 N 段命中，
这四类 GORM 都表达不出来，硬凑要靠 `Raw` 兜底，反而比直接写 SQL 更难读。
因此分工是：**能用 GORM 的地方用 GORM，表达不了的地方直接写 SQL**，
并且迁移文件全部手写、不用 `AutoMigrate`（向量列、HNSW、部分唯一索引、CHECK 约束它都生成不了，
混用必然导致 schema 漂移）。

### 3.4 模型推理放在 Python 边车，不编进 Go 二进制

ONNX Runtime 是 C++ 生态，Go 侧要链接它得引入 CGO，构建会从「静态二进制 + scratch 镜像」
退化成「要装编译工具链 + 依赖 glibc」。边车方案的代价是多一个容器、多一次 HTTP 往返，
换来的是主镜像仍然可以静态编译、`api` 与 `worker` 完全不知道模型的存在。

`api` **刻意不 `depends_on` 边车健康**：语义检索是可选能力，
用一个可选依赖把整个平台拦在启动之外不划算。边车没起来时文件管理与关键词检索照常工作，
只有语义检索返回 503，界面把原因说清楚。

### 3.5 PDF 当前只做存储与预览，正文索引待补

需求原文允许这样做（PDF 仅存储 + 预览），而 PDF 正文抽取要引入一整套解析链路
（过滤器链、字体与编码映射、版面还原），与本次交付的时间预算不成比例，
因此**排在最后，而不是不能做**。

这一点需要写明，因为本项目一度记录过一个相反的结论：验收语料里那 3 份 PDF
用 `pdftotext` 只取得到 77~104 个非空白字符，于是被记成「内嵌字体缺少 Unicode 映射，
即使接上解析库也什么都搜不到」。

**那个结论是错的。** 用 `pypdf` 实测，3 份 PDF 分别能提取出 **1005 / 996 / 941 个汉字**。
错误来自一次手工解析尝试：它只解了一层 `FlateDecode`，而实际的内容流过滤器链是
`[/ASCII85Decode /FlateDecode]`；字体资源名的正则也写成了 `/F\d+`，
而实际形如 `/F2+0`。**是解析代码的能力不足被当成了语料的缺陷。**

所以补上正文抽取之后，这几份 PDF 进索引没有障碍，语料不构成理由。

因此 PDF 的 `indexStatus` 是 `not_supported`（**当前状态，不是失败**），
界面上与 `failed` 用不同的标签、不同的颜色区分；详情页也不会给它「重新索引」按钮 ——
给一个按了也不会成功的按钮，比不给更糟。接上正文抽取后，这个状态就不需要了。

### 3.6 分类用「一个主归属 + 少量标签」，不做多归属

访谈语料里用户的诉求是「一个主要归属加少量标签，不要求同一文件被重复上传到多个目录」。
树负责「它属于哪个项目 / 哪类规范」，标签负责「它还有什么特征」，
两者都可以筛，但一份文件只有 `category_id` 一个主归属。

- 树用递归 CTE 做子树筛选：**选中父分类要能看到子分类下的文件**，
  否则点上层反而比点下层看到的少，与树形结构的直觉相反。
- 删除分类时 `ON DELETE SET NULL`，文件转为「未分类」而不是被一起删掉 ——
  删除一个整理维度，不应该删掉被它整理的东西。

### 3.7 上传进度、索引状态与文件状态三者分开

用户最容易误解的一件事是「上传成功 = 可以搜到了」。但保存原文件与建立索引是两个独立阶段，
后端在故障复盘中记录的正是这个误解（旧界面只显示上传是否成功，后台任务失败时用户毫不知情）。

因此界面上始终并列展示三件事：**文件在不在**（使用中 / 已归档 / 已删除）、
**索引到哪一步了**（待索引 / 索引中 / 已索引 / 索引失败 / 仅存储）、
**失败了为什么**（错误原因 + 重新索引入口）。
列表页还有一层轮询：只要有文件停在待索引/索引中，就每 1.5 秒静默刷新一次，
全部落定后自动停下，不留常驻定时器。

### 3.8 删除分两步，两步的反馈强度不同

「归档」和「删除」都是软状态，文件字节都不动，但语义不同：归档是「暂时不参与日常工作」，
删除是「我不要它了」。所以它们是**两个独立的位**而不是一个枚举 ——
一份已归档的文件被删除后，恢复时要能回到「已归档」而不是「使用中」。

删除本身又分两步，`DELETE /documents/:id` 只打 `deleted_at`，`/purge` 才真的抹掉：

- **`purge` 只对回收站里的文件生效**（否则 409）。想毁掉一份正在用的文件必须走两步，
  多出来的这一步就是误删可以停下来的地方。
- **反馈强度按「能不能反悔」分级**。软删除不弹确认框，改为在提示上挂一个 6 秒的撤销入口；
  真正毁数据的动作才弹红色确认框。对着一个随时能撤销的操作弹「确定吗」，
  只会训练用户闭眼点确定，等到真正不可逆的那次也一样点下去。
- 用**时间戳** `deleted_at` 而不是布尔：`IS NOT NULL` 照样能当布尔用，
  而「什么时候删的」是用户会问的问题。

过滤只写在 `store.ListFilter.where()` 这一处，列表、关键词检索、语义检索都经过它，
因此回收站里的文件在三个入口同时不可见。**这不是省事，是唯一能让它成立的做法** ——
三处各写一遍，漏掉任何一处就成了「删掉的文件还能被搜出来」，那比没有删除功能更糟。

删除与索引会撞车：文件可能在 worker 正在索引它的时候被彻底删除。
`CompleteIndexJob` 因此**先更新 `documents`，受影响行数为 0 就直接返回**。
没有这个顺序，那次写入会撞上外键（`document_chunks` 与 `index_jobs` 都随文档级联消失），
被记成一次失败并重试三次，而重试永远不可能成功。

### 3.9 日志：两个 core、按角色落盘、接上两条被绕过的流

原先用的是标准库 `log/slog` 的默认 logger：TextHandler、等级写死 `Info`、只输出到 stdout。
在容器里这意味着**日志随容器一起消失**，而且没法按等级过滤。现在换成 zap，
三个角色各写一个 JSON 文件并轮转。

**为什么是两个 core 而不是一个。** stdout 给人看要用 console 文本，文件给机器读要用 JSON。
直觉的写法是 `NewMultiWriteSyncer(stdout, file)` 配一个 encoder —— 那是错的：
encoder 是 **Core** 的属性、不是 WriteSyncer 的属性，多路复用发生在**编码之后**，
所以那样写会把 console 文本一并写进文件。正确做法是两个 Core 交给 `zapcore.NewTee`。

**为什么按角色分文件。** `api` 与 `worker` 是两个独立容器，而轮转是「重命名 + 新建」、
不做多进程同步：两个进程各持句柄、各按自己的计数切分，结果是交替丢日志、轮转互相踩。
跨容器的文件锁本身也不可靠，所以不加锁，而是接受一条**单副本约束**：
`docker compose up --scale api=3` 会打破这套命名。真要扩容，得改成按 hostname 分文件
或改用集中式收集。脚本里那套空库自测会同时起两套栈，同理用 `LOG_HOST_DIR` 隔开。

**目录不可写时拒绝启动**，而不是降级成「只写 stdout」。lumberjack 是第一次写才
`MkdirAll` 的，而 zapcore **会丢掉 Core 的 Write 错误** —— 一个不可写的目录会安静地
变成「文件日志根本不存在」，进程照跑、看起来一切正常，直到有人去找日志才发现。
所以装配时提前探一次：`MkdirAll` 加一次试开，失败就让进程起不来。

**换 zap 不会自动收编那两条绕过日志的流，必须显式接。** GORM 的 SQL 日志走 stdlib log
直接写 stderr，`gin.Recovery()` 的 panic 也是。后者换成
`gin.CustomRecoveryWithWriter(io.Discard, …)`，让 panic 只经 zap 一条路，
同时仍回那套 `{"code": …}` 的 JSON 错误契约（前端与验收脚本都依赖它）。

**脱敏的真正内容不是数据库口令。** GORM 默认打印的是**参数已插值**的完整 SQL，
批量插入时参数里带着 `chunk.Content`，也就是用户上传的正文。修法是把参数留在占位符里：
`logger.Config{ParameterizedQueries: true}`。这条比「口令别进日志」重要得多 ——
口令只在 DSN 里出现一次且已被换成 `REDACTED`，而正文会在每一次慢查询或出错时整批进日志。
验收时用一个正文含唯一哨兵串的文件实测过：库里 12 个片段都含它，日志里 0 命中。

**请求链路**：`X-Request-Id` 由中间件读取或生成，回写到响应头，并把带该字段的子 logger
放进 gin 上下文。放进上下文而不是每次现拼，是因为 `failInternal` 是个**没有接收者的自由
函数**、却又是所有 handler 错误路径的汇合点 —— 只有这样才能让它零改动就带上 `requestId`。
客户端给的 id 必须先消毒（只放行长度受限的 `[A-Za-z0-9._-]`）：夹一个换行就能在日志里
凭空伪造一整行。

**中间件顺序是顺路修掉的一个 bug。** 原来写的是 `gin.Recovery(), accessLog()`，
先注册的更靠外，所以 Recovery 包住了 accessLog —— **panic 的那次请求反而没有访问日志**。
现在是 `RequestID → AccessLog → Recovery`，并且有一个用例钉住它。

**一个诚实的限制**：索引是异步的，worker 处理任务时那次 HTTP 请求早已结束、而且在另一个
容器里。往 worker 日志里塞 `requestId` 是撒谎。真正存在的关联键是实体（`documentId` /
`jobId`），运维在一份文档上跨两个文件 grep。要做真端到端追踪，得给 `index_jobs` 加一列
并改造入队逻辑 —— 为一个没人提的需求做 schema 迁移，不做。

**耗时的单位写进键名。** 字段叫 `costMs` 而不是 `cost`，因为值是纯数字、单位不在里面。
用浮点而不是整数：这个系统的请求经常在 1 毫秒以下（健康检查实测 0.4~0.7ms），
`zapcore.MillisDurationEncoder` 做整数除法会把它们**全部压成 0** ——
这不是假设，是第一版的真实输出：切出 6 行访问日志，6 行全是 `"cost":0`，
而 console 那边显示的是 `434µs`。这个字段存在的意义就是分辨快慢，压成 0 等于白记。

### 3.10 顺序是用户可调的全局序列

`sort_order` 是**整张表一条序列**，不是每个分类一条、也不是每个视图一条。
归档区、回收站、某个分类的列表都是它的**子序列**，`ListDocuments` 因此只有一个
`ORDER BY d.sort_order, d.id DESC`，没有按视图分支。

之所以是一条全局序列，是因为**位置是与归档、删除并列的第三条正交状态**。
归档、移入回收站、恢复都不动 `sort_order`，所以一份归档文件被恢复出来还是回到原位 ——
与 §3.8 里「归档和删除是两个独立的位」同一套思路：把两件互不干扰的事塞进一个字段，
用户迟早会在其中一件事上丢掉自己原本的判断。

**接口收的是相对锚点 `afterId`，不是绝对下标。** 分类筛选后的列表只是全局序列的一段子序列，
下标在「全部文件」和「某个分类」两个视图里指向的完全是两回事；而「排在 X 之后」
在任何一段子序列里都唯一确定。置顶（`afterId: null`）是这个语义的边界情形：
在分类视图里它表现为排到本视图第一，同时也成为「全部文件」的第一 ——
这是「全局一条序列」的直接结果，不是缺陷，写在 §5。

**序号保持稠密（1..n），每次拖动整表重排**，而不是留出间隔、按中点插入、间隔耗尽再重排。
后者平时少写几行，代价是多出一条平时跑不到、真跑起来又最需要正确的分支
（而它恰好负责的又是「已经排了很多次」这种最难手算的情形）。在几百到几千份文件的量级上，
整表重写的开销可以忽略，所以选了只有一条路径的做法。写回用一条语句
（`unnest(?::bigint[]) WITH ORDINALITY`，数组由 `pq.Int64Array` 传入）。

**不加唯一约束。** 两次并发上传可能各自读到同一个 `MIN(sort_order)` 而写入同一个值，
唯一约束会让「两个文件并列最前」这种无害情形直接提交失败；并列由 `(sort_order, id DESC)`
兜底，与迁移前的列表次序一致。重排的整表 UPDATE 同样不该因为一次并发拖动而失败。

**重排只写 `sort_order`，不碰 `updated_at`。** 挪位置不是内容变更，
改「上传时间」属于撒谎 —— 列表上那一列的含义就是文件什么时候来的。

**一次性重排的取值来自迁移的窗口函数，而不是默认值。** 0004 的回填用
`row_number() OVER (ORDER BY created_at DESC, id DESC)`，与升级前的列表 ORDER BY
逐字相同，所以**升级前后界面上看到的一模一样**；`WHERE sort_order IS NULL` 保证重跑
不会覆盖用户已经排好的顺序。

**拖动排序不给撤销，拖入分类给。** 这不是不一致：排序的结果就在眼前，
拖回去的成本是一次同样的手势；而「移入分类」之后那份文件就从当前视图里消失了，
用户够不着它，所以按 §3.8 的规则挂一个 6 秒撤销。
反馈强度跟着「用户能不能自己走回去」走，而不是跟着「哪个操作更轻」走。

**用 pointer 事件 + 380ms 长按闸门，不用 HTML5 原生拖拽。** 原生 `draggable`
要先给行加属性，而每一行同时还要响应「点击打开详情」——两套手势在一个元素上抢事件；
它在触摸屏上根本不触发 `dragstart`。pointer 事件一套代码同时覆盖鼠标与触摸，
也才画得出跟手的文件条和行间插入线。380ms 这道闸门是为了让短按仍然是打开详情：
没有它，拖拽就把这个入口吃掉了。

## 4. 语义检索的标定与验证

### 4.1 向量生成

| 项 | 取值 |
| --- | --- |
| 模型 | BAAI/bge-small-zh-v1.5（MIT） |
| 导出 | `services/embed/tools/export_onnx.py` |
| 量化 | 动态 int8（QInt8 权重），产物 `model.onnx` 24 MB |
| 维度 | 512 |
| 池化 | CLS |
| 归一化 | L2（因此检索端可直接用余弦距离） |
| 单条上限 | 512 token |

### 4.2 切片参数

`ChunkSize = 400` 字符、相邻重叠 `80` 字符、单文档上限 `2000` 段。
按字符而不是字节计算——中文一个字 3 字节，按字节切出来的是半个字。

切在**行边界**上：语料是文档，一行往往就是一个完整条目（检查项、接口说明、规范条目），
从中间切开会让两个片段都读不出意思。行本身过长时退到句末标点，最后才硬切。

在验收语料上实测：7 份可抽取正文的文档切成 **29 段**，长度落在 167~400 字之间、
平均 335 字，最长的一段正好顶到上限而没有超过它。`internal/indexer/chunk_test.go`
里有一条用例专门盯着这个上限 —— 带上重叠尾巴之后装不下时，宁可不要重叠，也不能超过 400。

### 4.3 阈值标定

用 `SEMANTIC_MIN_SCORE` 控制余弦相似度下限。标定方法是把整份语料灌进去，
对每个提问取回全部结果（临时把阈值调到 0.01），观察「确实相关」与「其实不相关」两组的分布：

| 提问 | 预期命中的文件 | 首位相似度 |
| --- | --- | --- |
| 合并代码之前需要做什么检查 | 01_代码提交规范_v2.1.md | **0.7166** |
| 容器起来了但是服务还是用不了 | 09_本地部署故障排查_v1.3.txt | **0.6644** |
| 发布之后怎么确认没问题 | 05_星桥项目_发布检查清单_2026-09-18.txt | **0.6641** |
| 线上出故障之后要做哪些复盘 | 06_星桥项目_故障复盘_2026-09-21.md | **0.6195** |
| 团队成员平时是怎么找文件的 | 07_星桥项目_用户访谈纪要_2026-09-12.txt | **0.6180** |
| *（语料里没有对应内容时的最高分）* | — | 0.44 ~ 0.47 |

「相关」的下界是 0.60，「不相关」的上界是 0.47，中间是一段空档。
**0.5 是这段空档的中点**，取整好记，也离两侧都留了 0.03 以上的余量。

- 取 0.45 等于几乎不过滤，任何输入都会返回满屏弱相关结果；
- 取 0.60 会把「相关但措辞差得远」的结果一起挡掉，而这类结果恰恰是语义检索的价值所在。

换向量模型后必须重新标定，因此它被做成环境变量而不是常量。
复现命令：`python scripts/semantic_examples.py --reset`。

### 4.4 片段级还是文档级

相似度算在**片段**上（`document_chunks.embedding`），展示时按文档聚合，
文档的分数取它**最相关那一段**的相似度。这样既避免「长文档因为段数多而占满结果」，
又保证用户看到的每一段都是模型真正比对过的那段原文 —— 语义检索的片段不做二次截取，
截短反而丢掉了判断相关性的依据。

单篇最多返回 3 段（`DefaultSnippetsPerDoc`），单次最多返回 10 篇文档。

## 5. 已知限制

按「如果有人拿它上线会踩到什么」的顺序列出：

1. **没有身份认证与权限**。任何能访问该端口的人都能读写全部文件。
   本期是单机内网演示部署，访问控制被明确排除在范围外；
   真要多用户使用，这是第一个必须补的东西。
2. **PDF 内容检索不到**。当前 PDF 只做存储与预览，正文索引待补（§3.5）。
   这是**待补的功能**，不是语料的限制 —— 用 `pypdf` 实测那 3 份 PDF
   各能提取出约 1000 个汉字，理由与勘误见 §3.5。
3. **没有文件版本管理**。同一份文件重复上传会产生两个独立条目，列表里会出现同名项。
   故障复盘里提到的「用不同措辞描述同一问题→重复上传」正是这个场景。
4. **关键词检索没有相关性排序**。命中与否是二值的，排序规则是
   「文件名命中优先，其次按上传时间」。没有 TF-IDF 之类的打分，因为 pg_trgm 不提供。
   这一条只管**检索结果**：文件列表的次序由用户自己拖出来（§3.10），两者互不覆盖 ——
   在列表里把一份文件挪到最前，不会让它在新一次检索里也排到最前。
5. **相似度阈值绑定当前模型**。换成别的向量模型（甚至换量化方式）都必须重新标定，
   否则会出现「怎么搜都是空」或「不相关也返回一堆」。标定方法见 §4.3。
6. **索引是单消费者**。`worker` 只跑一个实例。任务队列本身支持多消费者
   （`FOR UPDATE SKIP LOCKED` 就是为此设计的），但当前编排里没有横向扩展。
7. **切片上限会截断超长文档**。单文档超过 2000 段的部分不建索引，
   详情页会给出提示。20 MiB 的中文文本约合五万段，写进 pgvector 要占几百 MB，
   必须在切的时候就封顶。
8. **语义检索的结果不显示命中词高亮**。关键词检索有片段窗口与省略号，
   语义检索给的是整段原文，两者都没有做词级高亮。
9. **分类树结构上不限深度，界面按两层设计**。三层以上会更拥挤，
   目前靠缩进与省略号处理，没有做折叠优化。
10. **Windows 上用 `curl.exe` 测非 ASCII 会得出错误结论**。
    命令行参数会先按 ANSI 代码页（中文机器上是 GBK）转码再发出，
    服务端收到的字节已经损坏。验收脚本因此用 Python 标准库手工拼 multipart 报文，
    见 `scripts/acceptance_api.py` 的文件头说明。
11. **`docker compose down -v` 会删光数据**，且重建镜像无法恢复。
    文档与 README 都做了显式警告。
12. **日志文件不支持同一角色的多副本**。文件名按角色固定（`api.log` / `worker.log` /
    `migrate.log`），轮转不做多进程同步，所以 `--scale api=3` 或同时跑两套栈
    都会让两个进程写同一个文件。前者要改成按 hostname 分文件或上集中式收集，
    后者用 `LOG_HOST_DIR` 隔开即可（脚本里的空库自测就是这么做的）。
13. **索引任务的日志无法关联到发起它的那次 HTTP 请求**。见 §3.9 末段：
    异步执行 + 跨容器，硬塞 `requestId` 只会得到一条撒谎的日志。
    跨进程的连接键是 `documentId` / `jobId`。
14. **拖动排序只在「使用中 / 已归档」两个标签页、且搜索框为空时可用**（§3.10）。
    回收站是暂存区，位置对它没有意义，所以连行首的抓手都不出现；
    搜索结果的次序由相关性决定，拖动它说不清会拖到哪儿去。
15. **不能跨页拖拽**。分页 10/20/50，一次只能在本页可见的行之间调位置。
    另外「拖到第一行之上」是**全局置顶**，在分类筛选视图里它同样会成为「全部文件」的第一 ——
    这是「全局一条序列」的直接结果，不是缺陷。
16. **排序没有自动化单测**。`store.MoveDocumentAfter` 的取数、摘行、拼接、写回都在
    `internal/store` 里，而这一层目前没有测试基建（同 §6.9 的理由）。
    现有证据是浏览器用例（重排 + 刷新后仍在 + 拖入分类 + 撤销）与手工接口验证
    （未知锚点 400、未知文件 404、自锚点无操作、空 body 置顶）。
